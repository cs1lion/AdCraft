## 0. 这份文档为什么现在写

渲染层替换这一轮把预演从**不成立**推到**成立**：

- 此前 720 帧全是从一个固定视点拍的，画面里没有任何几何体（CHANGELOG 有实测记录）
- 修完之后相机真正跟随分镜、色彩与深度通道同视角、交付帧不再带编辑辅助物

但"成立"不等于"可用"。下面这张对照表说明：**剩下的差距全部在资产与动画，不在管线**。

| 能力 | 10-04 Blender 成片 | 今天 three.js（修好后） | 差距性质 |
|---|---|---|---|
| 角色剪影 | 四肢 + 持枪 | 七段低模，无持枪、无姿态 | 资产 + 动画 |
| 非人角色 | 紫色异形（腿 / 尾 / 背刺） | 不支持 | **schema 缺一整类** |
| 场景装饰 | 环形坑、黄色导轨、平台 | 平面 + 网格线 | 词汇表 |
| 人物动作 | 走 / 打 / 持枪 | 身体整体位移，四肢建形后不转 | 动画 |
| 光照 | 双光源 + 柔和阴影 | 双光源 + 硬阴影 | 观感，可后置 |

## 1. 一个必须先讲清的历史事实：预览与产物曾经互相不同意

10-04 那批截图里最要紧的一组对照，是**同一个项目的两个界面**：

- **场景调度（3D 视口）**：角色是**蓝色方块**，带 gizmo、机位标签、右侧检查器
- **成片预演**：角色**有头有腿、持枪**，紫色异形生物，环形坑、导轨、建筑物

也就是说：作者在导演台拖动的是一个盒子，交付帧里长出腿来。这不是"3D 做得好"，是**视口与产物各自实现了一套词汇表**，两套必须靠人工保持一致。

替换方案 §3.6 讲的正是这件事，并且结论是**缺口单向**——Blender 那一侧一直是对的（`_build_lowpoly_human` 建了七段），错的是预览。2026-10-06 补的 `lowPolyHumanRig.ts` 把预览这一侧对齐了。

**但替换渲染层让这个不一致第一次变成硬矛盾**：渲染改用 `SceneScript3DPreview` 之后，视口和产物是同一份实现了——预览里缺什么，交付帧就缺什么，所见即所得从"目标"变成了"约束"。

这条约束是下面所有项目的共同前提：**任何想让成片出现的东西，必须先在视口里存在**。反过来也成立——视口里画着的东西，成片一定会有（今天开始还包括 gizmo，除非显式关掉）。

## 2. 差距清单（按"解锁的东西"排序，不按实现难度）

### 2.1 非人角色 —— `CharacterType` 只有一个值

**证据**：`apps/api/app/schemas/scene_script.py:28`

```python
CharacterType = Literal["lowpoly_human"]
```

10-04 成片里的紫色异形生物（腿、尾、背刺、明显不是人）在 schema 里**无处安放**。

**性质**：schema 加法。与渲染器完全无关——Blender 和 three.js 都受益，扩完枚举两侧同时获得这个能力。

**需要决定**（不是实现问题，是产品问题）：

- 枚举叫什么：`lowpoly_beast`？还是把"体型"（human / quadruped / insectoid）与"物种"分开？
- 比例是否也要参数化：现在 `CharacterAppearance` 只有 `color` / `height` / `scale` / `palette`，异形需要的躯干长度、腿数、尾长都无处声明
- 前端 `SCENE_SCRIPT_GEOMETRY` 是对 `PropType` / `EnvironmentType` 的**全映射**（新增 kind 不编译就红），所以扩枚举后必须同步补几何，否则会落到 `#FF2BD1` 的降级色——那个"响亮失败"信号要保住

**做完之后**：成片里能出现非人角色，且视口与产物一致。

---

### 2.2 持枪 —— 手没有可以握的姿态

**证据**：
- `PropType` 里有 `weapon`（`scene_script.py:39`），所以"枪"作为道具是能声明的
- `lowPolyHumanRig.ts` 的 `CHARACTER_RIG_FRACTIONS` 里手臂只有 `arm`（长度）与 `armHang`（垂挂位置），**没有任何关节角**
- `SceneProp.held_by` 能让道具跟着持有者的手走（`blender_converter.py:674-686` 会写 `location` 关键帧），但那是**位置跟随**，不是**握持**

所以今天能做到的是"枪浮在角色手边的固定位置"，做不到"手握着枪"。10-04 成片里是后者。

**依赖关系**：这一项**必须排在 2.4（姿态库）之后**。没有可摆的手臂，就没有"握住"这个姿态可言；先做持枪会得到一个需要硬编码的特例。

---

### 2.3 场景装饰 —— 词汇表里没有让画面"像场景"的东西

**证据**：`EnvironmentType`（`scene_script.py:49-63`）共 13 个值：`wall` / `pillar` / `floor` / `gable_roof` / `flat_roof` / `door` / `window` / `stairs` / `platform` / `tree` / `rock` / `fence` / `ground`。

10-04 成片里让画面成立的是：环形坑（crater）、黄色导轨（rail / track）、起降平台。**导轨与环形坑都不在枚举里**；`rock` 有，但一个 rock 不是一个坑。

**性质**：同样是 schema 加法，且与渲染器无关。

**需要决定**：枚举继续增长，还是引入"参数化几何"（一个 `crater` 带 `radius` / `depth`，而不是新增多个 kind）。后者更省枚举，但要求 `EnvironmentObject` 拿到参数字段——那是比"加两个枚举值"大得多的改动。**倾向后者，但值得单独评估。**

---

### 2.4 人物动作 —— 五个词没有任何一处被翻译成肢体姿态

**证据**（这是替换方案 §3.7 的结论，仍然成立）：

- `CharacterAction` = `stand` / `talk` / `walk` / `sit` / `gesture`
- 前后端搜 `walk|swing|cycle` 零命中；关键帧只插入 `location` 与 `rotation_euler.z`
- 前端唯一读 `action` 的地方是 `SceneScript3DPreview.tsx:215-219`：`talk` → 嘴张开，`gesture` → 头部前倾 15°
- **`walk` 的实际效果是身体滑动**（`stand` / `sit` 完全没有实现）

**做法**：姿态库。每个 action 对应一组关节角曲线，走路 = 腿前后摆 + 臂反向摆，正弦曲线在白模精度下足够。两侧共用同一套数据（放前端、后端读，或各自实现同一组曲线并用测试锁住）。

**为什么它最贵也最值**：这是唯一能把"滑动的木桩"变成"在走的人"的一项，而且它解锁 2.2（持枪姿态）。

**必须先解决的语义问题**：SceneScript 的关键帧语义目前是**最近关键帧步进**还是**插值**？两侧实现必须一致，否则"抬手"在某一帧开始、在另一帧结束。这一条不定下来，姿态库写出来也无法验收。

---

### 2.5 `SceneProp` / `SceneEnvironmentObject` 没有 keyframes

**证据**：两个模型都没有 `keyframes` 字段（`scene_script.py:230` / `:266`），schema 是 `extra="forbid"`。

这是同事那份计划的第一优先。评估见下节——**它确实该做且与渲染器无关**，但它解决的是"物"，不是"人"。

## 3. 与同事那份计划的差异（重要）

同事把优先级排成：① prop/environment keyframes → ② action 姿态库 → ③ 无人值守执行模型。

我的评估：**①② 同意，③ 同意，但缺了两项**（2.1 非人角色、2.2 持枪），而且**排序上有一处需要修正**。

### 已经存在、不该重做的部分

| 东西 | 在哪 | 结论 |
|---|---|---|
| 按帧插值的纯函数 | 前端 `characterPositionAtFrame`（`sceneScriptEditModel.ts:967`）+ 后端 `held_items._pose_at`（`held_items.py:69-95`） | 加 `PropKeyframe` 是**第三份**实现。应抽共享原语 |
| Blender 侧逐帧道具位移 | `blender_converter.py:674-686` 已在给 held prop 写 `location` 关键帧 | 只需把关键帧**来源**从"持有者手部"换成"道具自己的 keyframes" |
| 前端接入口 | `sceneScriptEditModel.ts:977-980` 现在直接返回静态 `prop.position` | 一行级改动，不是新链路 |
| 契约校验面 | `_validate_keyframes_in_range`（`scene_script.py:538`） | 已存在，只遍历 characters + cameras，要扩 |

顺带一个既有的文档缺陷：`held_items.py:70` 的 docstring 写着 "step, not interpolate"，而 `:89-95` 的代码是插值。文档已经和实现对不上。

### 他那份计划漏掉的（比"重复"更危险）

1. **不改生成器 prompt 就一帧都不会动。** `scene_script_generator.py:53-57` 把 props 的 JSON 形状**写死在 prompt 里**（无 keyframes）。schema 加字段只是"允许"，而 SceneScript 的真正生产者是 LLM。这是整件事的成败环节。
2. **held prop 会有两个位置来源。** `held_by` 与 `keyframes` 谁优先必须显式定义（`_validate_held_references`（`:493`）已确立"道具位置可由持有人推导"的先例）。
3. `_validate_keyframe_bounds`（`:538`）不覆盖 props/env，越界关键帧不会被拒。
4. `check:agent-canvas-contract` 比对 `agent-canvas-contract-manifest.json` 里 `SceneProp` / `SceneEnvironmentObject` 的属性清单，加字段必须同步 manifest，否则门禁红。

### 排序上的一处修正

同事的验收物是"汽车行进 + 车轮转动"的视频。这个例子选得好——它是**物**，正好落在 ① 的射程内。**但 ① 做完之后，画面里仍然只有会滑动的木桩人。**

如果目标是"从形到位变成动起来"，②（姿态库）比 ① 更接近那个目标本身。①解锁"物在动"，②解锁"人在动"。

建议：**①与②并行**（两者文件不重叠：①动 schema + `sceneScriptEditModel`，②动 `lowPolyHumanRig`），或者若只能串行，② 优先。

## 4. 不在这份清单里的（避免误判优先级）

- **光照 / 材质 / 阴影**：10-04 成片的观感更好，但那是"精细度"，与"能不能表达"是两个量级。替换方案开头就写明"只要形到位，精细度不做要求"。
- **无人值守执行模型**（同事的 ③）：切默认渲染器之前确实要解决，但它不提升画面质量，只提升可自动化程度。
- **FOV / 镜头语义**：schema 无镜头字段，当前硬编码 50 度，Blender 由 `lens` 推导。换渲染器后两者语义不一致，属于需要记一笔的债，不是当前瓶颈。
- **性能**：720 帧 77 秒对预演够用。不是瓶颈。

## 5. 一条方法论记要（这轮学到的）

这一轮抓到的四个 bug（相机 prop 只在挂载读一次、缺轴转换、`look_at` 未应用、编辑辅助物进交付帧）**形状完全相同**：每一处都是"某个机制存在但不生效"，而针对它们的测试全部测的是**纯函数**而不是**那个机制**。

- `shotCameraPoseAtFrame` 的插值数学有 20+ 条单测，全绿——但从来没人断言过相机真的动了
- 同事为修复写的规格，4 条断言全是**相对**的（"动过"/"不是种子值"/"位置超过三个不同"/"切镜距离 > 0.5"），一台被镜像摆放且没有朝向的相机四条全过
- 原规格用 `test.skip(boundary >= info.frames)` 条件跳过——换一份单镜夹具这条断言就静默消失

**两条纪律**（下一轮动手时直接照做）：

1. **断言机制的对象，不是它的输入。** 要证明"相机跟随"，就读运行中的相机；要证明"深度通道产出"，就读磁盘上的 PNG；不要读纯函数的返回值。
2. **断言绝对值，不是相对关系。** 相对断言（"变了""不是那个值"）对"错得离谱但方向一致"的实现全部免疫。修完要拿**真实渲染产物**做像素对比，并明确写出修复前的数字——不然"改好了"和"改成了另一种错"分不开。

变异复验是唯一能证明规格有牙的手段，而且要**逐层**做：去轴转换 → 4 条失败；去 `look_at` → 4 条失败；移除整个机制 → 8 条失败。只做一次变异，会把"规格只覆盖了最外面一层"这件事漏掉。

## 6. 建议的下一步

按"解锁的东西"排，不按实现难度：

1. **2.4 姿态库**（含先定下关键帧语义是步进还是插值）——把木桩变成人
2. **2.1 非人角色**（`CharacterType` 扩枚举 + 体型参数化 + 前端几何同步）——schema 加法，两个渲染器同时受益
3. **2.5 prop/environment keyframes**（同事的 ①，注意 §3 的四个漏项）——解锁物
4. **2.2 持枪**（依赖 1 完成）
5. **2.3 场景装饰**（枚举 or 参数化几何，值得单独评估）

每一项做完的标准：**用真实场景渲一段视频，用像素对比说明画面变成了什么样**，不是用测试数量说明。

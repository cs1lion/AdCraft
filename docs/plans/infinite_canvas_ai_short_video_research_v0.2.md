## 1. 本轮讨论形成的总判断

产品的核心体验可以暂时概括为：让创作者感觉“我是在画一个视频，而不是在操作一个复杂的视频编辑器”。本轮新增一个重要变量：Audio Gen 不应只被看作“生成一条音轨”的能力，而可以成为叙事与时间组织的一部分。

无限画布不是传统 Timeline 的简单替代品，而更接近一个“叙事空间”：Scene 是叙事单元，Scene 之间的空间关系、连续性、镜头变化和分叉，共同承载故事结构。在多角色语音场景中，声音还能成为镜头时序的重要锚点：先确定说什么、谁说、怎么说、何时停顿，再让画面围绕这些节奏组织。

同时，LLM 不应只是帮助用户把一句话润色成 Prompt，而应承担更高一层的“镜头衔接与导演辅助”职责；Preview 也不应只是看成片效果，而应成为低成本的“审片—反馈—修改”循环。Audio 与 Video Prompt 则应被视为同一叙事意图下的两种执行通道，而不是互相争夺“谁才是主 Prompt”。

### 核心定位
> 真正值得做的，不是继续堆“无限画布功能 + 视频编辑功能”，而是让“分镜之间如何连起来”成为系统主动帮助创作者思考、表达和修改的问题。

| 层级 | 主要职责 | 用户心智 |
|---|---|---|
| Canvas | 想、搭、探索故事结构；表达 Scene 之间关系 | 我在构建故事 |
| Scene | 编辑单个镜头及其状态 | 我在创作这一镜 |
| Transition / Relation | 表达镜头之间如何衔接 | 我要它这样讲过去 |
| Preview | 低成本验证叙事、连续性与画面 | 我在审片 |
| Final Render | 正式制作/渲染 | 确定后再出最终素材 |

> **阶段性判断：** Canvas = 故事空间；Timeline = 精确时间。两者应该联动，但不要互相替代。

## 2. 讨论演进：从交互清单到“叙事空间”

最初问题是：无限画布 + 视频短片创作在交互上有哪些值得做的设计，尤其是拖拽等。第一轮提出了一组可能的交互方向。随后讨论没有继续无差别扩充，而是主动收敛到用户更看中的 1、2、3、4、13，同时对“17 连线”保留但不全量采用。

### 2.1 第一阶段：把拖拽建立成“第一语言”

讨论中提出：素材、Scene、音乐、参考图等，不应该主要依赖“点击新建—弹窗—配置”的传统流程，而要让拖拽本身产生语义。

- 素材 → 拖到画布：创建镜头。
- 图片 → 拖到图片 / Scene：作为参考图或素材。
- 人物 → 拖到镜头：成为该镜头的角色/输入。
- 音乐 → 拖到时间区域：形成音轨。
- 镜头之间拖放：改变顺序或建立转场/关系。

> **重要判断：** 拖拽不只是移动 UI 元素，而应该是“用户在表达意图”。

### 2.2 第二阶段：吸附不是纯视觉，而是语义吸附

讨论进一步提出，拖拽时应有吸附，以降低精确摆放成本。但更重要的是“吸附到哪里意味着什么”：左右可表达前后镜头，上下可表达素材/参考关系，卡片内部可表达素材归属，两个镜头之间可表达转场或新镜头插入。

因此吸附应从“几何便利”升级为“语义提示”。但这也意味着产品不能为了丰富语义而把所有关系都画出来，后续必须做取舍。

### 2.3 第三阶段：二维无限画布不强制等于时间轴

讨论中明确反对“把 X 轴直接当传统时间轴”的思路。二维空间更适合表达故事关系，例如主线、回忆、支线、不同叙事路线。最终时间顺序可以由系统生成或同步到独立 Timeline。

### 2.4 第四阶段：Scene 从“卡片”变成“镜头编辑单元”

Scene 不应只是一张缩略图。它至少应包含可理解的画面、Prompt/意图、时长、画幅，以及人物、环境、道具等输入/状态。用户应尽量能直接在 Scene 卡片上进行调整，而不是频繁跳页面。

### 2.5 第五阶段：分叉把“版本管理”变成“叙事探索”

讨论中对第 13 条“分叉”比较认可：同一前置 Scene 可以探索不同连接方式，例如 A=连续运动、B=特写切换、C=环绕镜头，然后比较再选一条。这样分叉不是简单“文件另存为”，而是故事探索。

## 3. 当前重点保留的 1 / 2 / 3 / 4 / 13

当前共识不是“全部做满”，而是先建立一个最小但有独特性的核心闭环：**拖拽构建 → Scene 表达 → Scene 间关系 → Preview → 反馈/修改 → 再 Preview → 选择分支/正式制作。**

| 编号 | 当前含义 | 需要保留的关键细节 | 主要风险 / 取舍 |
|---|---|---|---|
| 1 拖拽 | 拖拽作为第一语言 | 拖素材、镜头、参考、音乐、顺序、转场；移动本身产生意图 | 语义过多会让用户不知道拖到哪里做什么 |
| 2 吸附 | 拖拽落点提供语义吸附 | 左右/上下/内部/镜头间；强调“吸附意味着关系” | 不能只追求吸附丰富度，否则会变成复杂工作流 |
| 3 二维空间 | Canvas 承载故事结构，不强制 X 轴是时间 | 主线、支线、回忆、方案探索都可以存在 | 需要另有轻量时间轴保证精剪能力 |
| 4 Scene 卡片 | Scene 是一个“小编辑器” | 画面 + 状态 + 意图 + 时长 + 关系；直接操作 | 避免把卡片做成参数面板 |
| 13 分叉 | 同一段关系可探索多个叙事方案 | 比较/播放/选择；保留多个路径 | 分支太多会迅速产生管理负担 |

## 4. Scene 间表达：核心深挖框架

讨论目前识别出 Scene 间至少有四种不同性质的关系：

| 关系类型 | 它在表达什么 | 是否适合显式连线 | 更推荐的初步呈现 |
|---|---|---|---|
| 时间关系 | A 在 B 之前/之后；顺序改变 | 通常不需要 | 画布位置 / 顺序 / Timeline 同步 |
| 叙事关系 | A 如何把观众带到 B；为什么这样切 | 有条件地需要 | 轻量 Transition Intent / 关系提示 |
| 连续性关系 | 人物、道具、方向、动作、空间如何保持 | 通常不应画成大网线 | 状态标记 / 需要时提示问题 |
| 生成依赖 | B 的生成依赖 A 的参考、状态或某个结果 | 可以隐藏 | 系统内部数据关系；必要时局部可见 |

### 4.1 为什么不主张“所有关系都画线”

此前提出了多种线型：时间关系、参考关系、继承/复制关系、注释/想法、排除/废案等。但很快发现，如果这些全部常驻，Canvas 很容易从“叙事空间”退化成“节点工作流编辑器”。因此当前原则是：

- 默认的前后时间关系不必画线，因为空间顺序本身就能表达。
- 只有当用户需要理解复杂的非线性关系时，才让关系显现。
- 连续性问题更适合用状态、标记、提示去表达，而不是铺一张关系蜘蛛网。
- 关系线应成为“解释关系”的工具，而不是“建立连接”的必选操作。

### 4.2 Scene 之间最值得做的“关系”不是静态关系，而是“转变”

如果 Scene 01 是“女孩站在街道上”，Scene 02 是“女孩进入建筑内部”，普通 AI 可能分别生成两个镜头，但真正的创作问题是：观众如何从第一镜头自然地进入第二镜头？

因此可以把 Scene A → Scene B 之间增加一个 **Transition Intent（转变意图）** 的概念。它不是单一 Prompt，而是一种对镜头如何转变的结构化理解。

> **核心洞察：** LLM 不再只是“帮写下一镜头 Prompt”，而是在解释“两个镜头之间应该发生什么”。

### 4.3 可以给创作者几种衔接方案，而不是替用户决定

| 方案 | 示例 | 强调点 |
|---|---|---|
| A 连续运动 | 女孩转身 → 摄影机跟随 → 进入建筑 | 空间连续性 |
| B 视线/特写切换 | 特写眼睛 → 切到房间里的相同视线方向 | 人物主观感 / 情绪 |
| C 时间/空间跳跃 | 女孩抬头 → 天空 → 夜景 → 房间 | 时间变化 / 视觉转场 |
| D 视角切换 | 街道远景 → 建筑内部 → 女孩进入 | 视觉冲击 / 信息揭示 |

这里形成了一个重要设计原则：**LLM 负责扩展创作者的镜头想象、解释不同方案的叙事含义；创作者保留最终选择权。**

## 5. 场景一致性：Continuity State

“场景一致性”被明确视为核心问题之一。仅靠两张参考图相似，并不能解决“人物在上一镜头做了什么、下一镜头应该如何继续”的问题。

因此讨论提出 **Continuity State / 持续世界状态**：把跨 Scene 的事实从静态参考升级为会随故事变化的状态。

| 状态维度 | 示例 | 下一镜头如何使用 |
|---|---|---|
| 人物 | 女孩 | 保持同一人物身份 |
| 服装 | 黑色风衣 | 继续继承 |
| 道具 | 透明雨伞，右手 | 避免下一镜头无故换手/消失 |
| 动作状态 | 站立 → 转身 → 行走 | 根据上一镜头的动作阶段继续 |
| 空间 | 夜晚街道 → 建筑入口 | 保持空间方向逻辑 |
| 镜头方向 | 人物朝右 | 下一镜头可继续保持或有意识反转 |
| 情绪 | 紧张 | 为下一镜头提供状态基础 |

这个设计把“连续性”从“画面像不像”提升成“世界状态是否连续”。

一个非常具体的失败例子是：Scene 01 里女孩右手拿伞，Scene 02 变成左手；或者上一镜人物向右运动，下一镜突然向左，且没有叙事意图。这些不一定是单镜头生成质量问题，却会严重破坏拼接后的真实感。

因此在 Scene 拖拽、排序、生成下一镜头之前，可以做 **Continuity Check**：检测人物位置、动作、道具、方向等是否出现异常，并提出修复建议。

## 6. LLM 的创新位置：从 Prompt 助手到“导演辅助”

> **核心定位：** LLM 不应该只负责“把用户的话写成长 Prompt”，而可以承担“理解叙事意图、分析 Scene 间关系、提出镜头衔接方案、维护连续性状态”的中间层角色。

### 6.1 用户说的是意图，系统内部形成执行理解

例如用户说：“这一镜头接上一镜的时候，女孩手里的伞不能消失。”这不是一个简单的 Prompt 修正，而是：

- 识别用户关注对象：道具 / 伞。
- 识别关系范围：跨 Scene 连续性。
- 识别约束：不能丢失、最好保持手持关系。
- 影响下一镜头生成的 Continuity State。
- 必要时重新生成 Scene 或 Transition，而不是只改一句文字。

### 6.2 用户可以只说“感觉不对”，LLM 再帮助具体化

例如用户说：“我想让这里自然一点。”系统可以把自然拆成空间连续、动作承接、运动方向一致、剪辑时机等可能维度，然后提出少量可选解释，而不是逼用户先学会视频术语。

### 6.3 LLM 介入的边界

| 适合 LLM 做 | 不应强行替用户做 |
|---|---|
| 理解模糊表达 | 替创作者选唯一叙事方案 |
| 分析 A → B 的连续性 | 把复杂参数全部暴露给用户 |
| 提出多种 Transition Intent | 擅自覆盖用户原意 |
| 把自然语言转成结构化执行计划 | 把内部实现方案冒充为唯一产品设计 |

## 7. 480P Preview：从预览变成“低成本审片”

讨论明确认为：480P Preview 的价值不只是“正式生成前看一下”，而应该成为完整的低成本创作阶段。其中音频尤其不应被压到“最后再听”：画面虽然是 480P，但声音应尽量接近可判断节奏与表演的质量，以便用户真正判断对话停顿、转场时机、情绪与信息密度。

因此正式制作与创作过程应被分开：

```text
构建 → Preview → 修改 → 再 Preview → 确认 → Final Render
```

| 阶段 | 目标 | 用户行为 |
|---|---|---|
| 构建 | 搭 Scene / 组织故事 | 拖拽、排序、分叉、补充状态 |
| Preview | 验证叙事、连续性、镜头运动、节奏 | 播放、Scrub、指出问题 |
| 修改 | 快速纠错和试错 | 自然语言 / 点击对象 / 框选 / 画运动意图 |
| 再次 Preview | 验证修改是否解决问题 | 重复审片循环 |
| Final Render | 正式制作 | 确认后生成正式素材 |
| Audio 预演 | 先让对白/声音成立并作为节奏锚点；必要时据此调整 Scene 时长与镜头转变 | 让“听起来是否对”更早进入创作闭环 |

### 7.1 画布与 Preview 可以形成联动

不仅可以拖底部 Timeline 播放头，还可以设计“从左向右拖”来 scrub 全局视频；用户在 Canvas 里移动故事时，也能快速感知时间与叙事的关系。

轻量时间轴可以常驻底部，需要精剪时向上展开；这保持“Canvas = 创作、Timeline = 精确时间”的关系。

## 8. 用户修改能力：五个维度 + 空间化入口

这是本轮讨论中被明确认为“非常重要、值得挖掘和创新”的用户体验。核心原则是：不要一上来给用户一个巨大的专业参数面板，而要让用户直接表达“哪里不对、想变成什么”。

### 8.1 自然语言是第一层修改接口

用户可以直接说：“这里太快了，女孩刚转身就切了，我想让这个动作完整一点。”系统应理解成：延长动作时长、推迟剪辑点、保持后续进入时机、重新生成 Transition Preview。

这意味着“用户怎么说”与“系统怎么执行”是两个层面。用户不需要知道内部参数。

### 8.2 指哪改哪：空间指向

用户点击人物脸、背景、画面空白区域时，可以产生上下文相关的修改入口：

- 人物：表情、发型、姿势、视线、服装。
- 背景：建筑、天气、灯光、空间元素。
- 空白区域：构图、景别、镜头方向、运动。

这里的关键不是“增加菜单”，而是让系统知道用户在说哪一个对象。空间指向会减少语言歧义。

### 8.3 用画线 / 箭头表达镜头运动

讨论进一步提出：很多“镜头往右绕一点”“朝这里移动”用自然语言很难说清，但用户用鼠标画一条箭头/轨迹非常直观。系统可以把轨迹理解成 Camera Motion / Composition Intent，再转成可执行提示。

这是“输入想法”与“执行指令”之间非常典型的一座桥。

| 维度 | 典型表达 | 对应问题 |
|---|---|---|
| ① 内容 What | “把女孩改成短发” | 画面里有什么 |
| ② 镜头 How to see | “从背后拍”“近一点” | 观众如何看 |
| ③ 动作 What happens | “她先看左边，再转身” | 画面里发生什么 |
| ④ 连贯性 Continuity | “继续保持右手拿伞” | 和前后镜头如何衔接 |
| ⑤ 节奏 / 叙事 Story | “这里停顿久一点再切” | 什么时候发生、情绪怎么走 |

## 9. 分叉与多叙事方案

分叉机制不只是版本管理，而是帮助创作者比较不同叙事选择。

典型场景：Scene 02 → Scene 03 之间有不同衔接方式，可以同时保留：

| 分支 | 连接方式 | 强调点 |
|---|---|---|
| A | 连续运动：转身 → 跟拍 → 进入 | 空间连续性 |
| B | 特写/视线切换 | 人物情绪 |
| C | 环绕 / 视角变化 | 视觉冲击 |

用户可以直接播放多个版本，而不是反复覆盖同一个结果。这样 Preview 就变成“方案评审”，而不仅是“找错误”。

但分支也有明显风险：数量很快会爆炸。因此应该考虑“局部分叉”，而不是鼓励整个项目无限树状化。

## 10. 用户表达 / 执行指令 / 输入想法：三层模型

> **本轮新增且需要长期保留的原则：** 产品应同时保留三个层次：用户表达意图、执行指令、输入想法。三者可以互相转换，但不要要求用户理解内部参数。

| 层次 | 定义 | 例子 | 对产品的意义 |
|---|---|---|---|
| 用户表达意图 | 用户用自然语言表达想要什么 | “这里太快了，动作完整一点” | 保持创作者自由表达 |
| 输入想法 | 用户通过空间/操作直接表达视觉想法 | 点击人物、框选、拖拽、画箭头 | 让不会写 Prompt 的用户也能创作 |
| 执行指令 | 系统将意图转换后的结构化任务 | 延长转身动作、推迟切点、保持伞在右手 | 连接 UI / LLM 与实际生成能力 |
| Audio 叙事输入 | 例如先生成多角色对白，并指定语速、语气、停顿 | 把声音变成时间与表演的可操作输入，再驱动画面组织 | |

需要避免的情况是：让 UI 直接暴露执行指令，使用户不得不学习参数；或者反过来让系统完全隐藏执行意图，使用户无法知道系统理解错了什么。

更理想的状态是：系统可以在必要时让用户看到“我理解你的意思是……”，用户可以调整；但平时不强迫用户操作内部结构。

## 11. 施工交付：研究记录与施工方案如何配合

本轮最后一个重要结论不是产品功能，而是“怎么把设计交给更了解代码的施工方”。

不建议把全部多轮聊天原样丢给施工方并让对方自己判断。原始讨论有价值，但其中同时存在探索、备选、反对意见和未决问题。

更合适的是“一主一辅”：

| 材料 | 用途 | 内容 |
|---|---|---|
| 主文档：施工方案 | 真正执行的依据 | 目标、已确认交互、本阶段范围、状态模型、用户流程、验收标准、明确不做什么 |
| 辅文档：研究记录 | 解释为什么这样设计 | 保留本轮思维碰撞、方案比较、风险、淘汰理由、开放问题 |

### 11.1 推荐在施工方案中明确四种状态

| 标记 | 含义 | 施工方如何理解 |
|---|---|---|
| Confirmed / 已确认 | 经过讨论已形成共识 | 优先保障行为与体验 |
| Proposal / 建议 | 当前推荐，但仍可验证 | 可结合代码与原型调整实现 |
| Open / 待决策 | 还在研究 | 不要自行假设为强需求 |
| Out of Scope / 暂不做 | 本阶段明确不进入施工 | 不要因讨论中出现过就顺手实现 |

### 11.2 给施工方的自由度应该落在“实现方式”，而不是“产品目标”

产品方案应该明确：为什么做、用户看到什么、用户怎么操作、系统应该产生什么结果、关键状态是什么、什么算完成。

但不要强行锁死：React 组件怎么拆、状态管理用什么、某个数据结构如何组织、具体 API 怎么串、哪些现有组件复用。

> **原则：** “产品语义要明确，代码实现要留空间。”施工方可以更了解项目代码，因此应该允许其在既定产品目标与验收标准下做技术和结构优化。

## 12. 已确认 / 待决策 / 暂不做 / 施工自由度

本轮结束时，建议暂时维护如下状态。它不是永久结论，而是后续讨论的基线。

| 类别 | 目前内容 |
|---|---|
| 已确认 / 共识 | 无限画布作为叙事空间；1 拖拽、2 吸附、3 二维叙事空间、4 Scene 卡片、13 分叉作为重点方向；场景一致性是核心问题；LLM 应进入 Scene 间的叙事衔接；480P Preview 应成为低成本审片环节；用户应有自然语言 + 空间化修改入口；应区分用户表达意图与系统执行指令；施工方拥有实现自由度。 |
| 待决策 / Open | Scene A → Scene B 的具体关系模型（已答：**标签**而非连线，见 §15 表 §13 行）；Continuity State 的最小数据范围（已落地：身份/方向/手持物/服装/情绪，见 §15 表 §5 行）；Transition Intent 如何被用户编辑（已答：提案面板登记 + **镜头条可撤销登记** + 应用即登记，见 §15 表 §4.2 行）；仍开放：LLM 提案出现的时机与密度（当前为默认关、作者显式开启）；分叉的最大组织复杂度（当前上限 4 且界面明示）；Preview 修改入口如何保持简单。 |
| 暂不做 / Out of Scope | 不把所有关系都做成常驻连线；不把 Canvas 做成复杂节点工作流；不把 Preview 变成参数面板；不强迫用户学习镜头术语；不要求第一阶段一次加入大量交互。 |
| 施工自由度 | 具体组件、状态组织、技术方案、已有代码复用、动画实现、数据结构等由施工方结合项目代码判断；但不得以实现便利为由改变已确认的用户意图与核心行为。 |

> **值得长期保持的设计目标：** 最终希望形成的并不是“会生成视频的无限画布”，而是一个让创作者可以在空间中构建故事、在 Scene 间表达镜头变化、借助 LLM 扩展叙事、通过 480P Preview 低成本审片，并能用自然语言与视觉操作快速修正的创作系统。

## 13. 下一轮研究建议：Scene A → Scene B 的关系模型

按照当前讨论节奏，下一轮不宜再同时展开大量新功能。最值得继续深挖的是“Scene A → Scene B 的关系表达”。

1. 先定义 Scene 间有哪些真正有价值的关系，并区分它们的语义。
2. 逐项判断：是否需要显式可视化、何时出现、默认隐藏还是默认显示。
3. 研究 Transition Intent 应该由用户如何表达、LLM 如何提出、用户如何修改。
4. 把 Continuity State 与 Transition Intent 连接起来：前者回答“什么必须连续”，后者回答“什么发生改变”。
5. 最终再决定连线是不是必要，以及哪些关系适合线、标签、状态、提示或完全隐藏。

## 14. Audio Gen 如何成为叙事骨架：语音、视频 Prompt 与剪辑的协同

本轮补充的出发点是：当前已经具备 Audio Gen，而且支持多角色、内容、语速、语气等控制。那么音频就不应该只在“视频做完后再配一条声音”，而应该前移到创作阶段，成为帮助构建 Scene、节奏与叙事关系的一种输入。

最值得进一步研究的问题不是“音频和视频 Prompt 谁更重要”，而是建立一个更高一级的“叙事意图”作为共同上层。Audio 与 Video Prompt 都是这个上层意图的执行通道；在不同类型的 Scene 中，两者的主导权可以动态切换。

### 14.1 先确定一个核心层级：不是 Audio vs. Video，而是“叙事意图 → 多通道执行”

| 层级 | 职责 | 用户是否需要直接操作 |
|---|---|---|
| Narrative Intent / 叙事意图 | 人物关系、发生什么、情绪如何变化、观众此刻应该注意什么 | 需要：允许自然表达，也允许模糊表达 |
| Audio Intent / 声音意图 | 谁说、说什么、怎么说、何时停顿、声音先后与情绪节奏 | 需要：可生成、可局部修改、可锁定 |
| Visual Intent / 画面意图 | 拍什么、怎么看、怎么运动、场景如何变化、人物动作如何呈现 | 需要：可 Prompt、可空间化表达、可锁定 |
| Edit / Timing Plan / 编辑与时间计划 | 切点、镜头长度、声音先行/后延、动作完成度与整体节奏 | 可被系统辅助，也应可人工干预 |

> 用户可以只说一句“这段像争吵，但最后突然安静下来”，系统再同时生成 Audio Intent、Visual Intent 与 Timing Plan。这样就避免把 Prompt 当成唯一创作入口。

### 14.2 谁占主导地位？建议采用“场景动态主导”，而不是永久固定谁更大

如果强行规定 Audio 永远主导，视觉创作容易被对白绑死；如果 Video Prompt 永远主导，又会浪费已经具备的多角色语音能力。更合理的是：上层叙事意图固定为最高优先级，Audio / Visual 根据 Scene 类型成为不同程度的“时间骨架”。

因此产品层面可以允许每个 Scene / Transition 带一个“叙事主导模式”，但不一定把它做成用户必须选择的复杂参数。很多时候系统可以由 LLM 根据内容自动提出：“这一段建议以声音为时间锚点”。用户只需要接受、修改或忽略。

| 场景模式 | 主要时间骨架 | 另一通道如何跟随 | 典型例子 |
|---|---|---|---|
| Dialogue-led / 对白主导 | Audio | 镜头时长、切点、反应镜头围绕说话、停顿、接话组织 | 两人对话、采访、独白、争吵 |
| Visual-led / 画面主导 | Visual | 音乐、声音效果、环境声跟随动作与视觉节拍 | 动作、奔跑、战斗、纯视觉叙事 |
| Co-led / 双主导 | Audio + Visual 同时构成节拍 | 系统寻找声音与动作的共同切点、错位点或呼应点 | MV 感场景、情绪蒙太奇、广告 |

### 14.3 一个重要创新：把“语音生成”从音轨变成可操作的“时间锚点”

现在很多产品把 Audio Gen 的结果理解为一个文件：生成 wav/mp3 → 拖到 Timeline。对于本产品，更有价值的抽象应该是“可编辑的表演事件”。

于是“生成一段对白”可以天然产生一组时间事件。系统可以据此反推：这一句应该落在哪个 Scene、哪些镜头适合切反应、哪里可以使用 J-cut（声音先进入下一画面）或 L-cut（画面已切走但声音继续），以及哪里应该保留停顿而不是急着切。

| Audio Event 字段 | 示例 | 为什么重要 |
|---|---|---|
| Speaker / 角色 | 女孩 | 建立多角色关系与角色连续性 |
| Text / 内容 | “你终于来了。” | 可与剧本、Scene 叙事意图同步 |
| Delivery / 语气 | 压低声音、克制、带一点怀疑 | 影响人物状态与画面节奏 |
| Tempo / 语速 | 偏慢 | 决定对白占据的时间长度 |
| Pause / 停顿 | “你……终于来了。” | 可直接成为镜头切换或情绪停顿锚点 |
| Timing | 00:08.4–00:11.6 | 让 Scene / 镜头时长有真实时间依据 |
| Voice Identity | 角色 A 的固定声线 | 维持跨 Scene 人物连续性 |
| Generation Version | V3 | 允许局部重新生成而不破坏整条音轨 |

### 14.4 Audio 与 Video Prompt 怎样协同：不要互相覆盖，而要共享一个“Scene Intent”

建议每个 Scene 都拥有一个用户可理解、系统可拆解的“共同创作意图”。用户可以从任一入口进入，但系统最终把信息汇合到同一个 Scene Intent。

这里“谁主导”的答案会变得更清楚：不是“Audio Prompt 覆盖 Video Prompt”，而是两者都服从同一个上层 Scene Intent。真正有冲突时，系统应该把冲突暴露出来，而不是静默覆盖用户的某一方。

### 14.5 LLM 可以做得更进一步：从“写 Prompt”变成“声音驱动的镜头编排器”

当 Audio Gen 已经存在时，LLM 可以利用语言内容、角色轮次、停顿、语气与情绪变化，主动提出镜头组织，而不是等用户写完整镜头 Prompt。

这会让产品出现一个很有辨识度的能力：**“先听懂，再决定怎么拍”。** 用户甚至只给一句对白，系统就可以给出一个低成本的 Shot Plan。

### 14.6 “如果已经做了引导，剪辑的地位是否要重新思考？”——是，但不是取消剪辑

一旦 Scene、Audio、Transition、Continuity 都被系统提前组织，传统“把已经生成的素材重新拼一遍”的剪辑工作确实会减少。但剪辑不会消失，它更可能从“修补工具”变成“节奏与叙事控制器”。

因此可以提出一个新的产品定位：不是“不要剪辑”，而是“把剪辑前移成创作意图，并把后期剪辑升级成高层次选择”。最终仍然需要手工编辑入口，尤其是用户已经形成明确审美判断时。

| 传统剪辑的主要任务 | 引导式 AI 工作流后的对应任务 |
|---|---|
| 找合适素材 | 系统先根据 Scene Intent 与 Audio/Visual 计划组织候选素材 |
| 硬切解决镜头衔接问题 | 生成阶段就产生 Transition Intent，减少低质量拼接 |
| 反复拉齐对白与画面 | Audio Event 提供时间锚点，生成时尽量直接对齐 |
| 靠后期补救人物/场景不连续 | Continuity State 在前置阶段持续约束 |
| 大量时间用于技术性修剪 | 编辑更多回到节奏、视线、信息揭示与情绪选择 |

### 14.7 音频必须真正“可编辑”，否则它无法成为创作骨架

如果 Audio Gen 只是一次生成一整条音轨，用户一旦修改一句台词，就被迫重新生成整段，前面的时间组织也会失效。建议从一开始就把可编辑性作为数据模型的一部分。

值得注意的是，“拖音频边缘改变时长”不一定等于简单拉伸波形。对于语音表演，轻微调整可以采用时间处理；较大变化可能需要重新生成，以避免机械感。产品不必把底层技术差异暴露出来，但应保持“用户只是在改时间”的心智模型。

| 编辑层级 | 用户操作 | 系统行为建议 |
|---|---|---|
| 内容层 | 改一句话 / 换一个词 | 只重新生成对应 Audio Event，并让后续时间重新计算或提示影响范围 |
| 表演层 | 更慢、更冷淡、情绪更强 | 局部重新生成；尽量保持 Speaker Identity 与前后音色一致 |
| 结构层 | 两句台词对调 / 删除 / 插入 | 重排 Audio Event；同步更新受影响 Scene 与 Transition |
| 时间层 | 把这句拖长 / 增加停顿 | 优先使用自然时间调整；超出合理范围时再建议重新生成 |
| 同步层 | 希望嘴型/动作对齐 | 重新计算与 Visual Beat 的同步关系，并标记受影响镜头 |

### 14.8 Preview 工艺要改变：480P 画面 + 可判断的声音，比“低清画面 + 临时音频”更有价值

因为故事节奏、对白表演、声音先行/后延、停顿与反应镜头，都只能真正听出来。因此 Preview 阶段虽然可以把视频降到 480P，但音频应尽量保持足够好的可判断质量。

| Preview 阶段重点检查 | 应让用户能直接判断什么 |
|---|---|
| 对白 | 角色是否自然、轮次是否舒服、语气是否符合人物 |
| 节奏 | 一句话是否太快、停顿是否有价值、切点是否抢节奏 |
| 镜头 | 是否在正确的词/动作/情绪节点发生变化 |
| 声音-画面关系 | 声音是否可以先于画面、画面是否应该留下来听完 |
| 连续性 | 人物、道具、运动方向、情绪是否从 A 自然到 B |
| 整体密度 | 信息是否太满；是否需要留白、环境声或无对白镜头 |

### 14.9 一个值得探索的“导演式 Preview”：先做 Animatic，而不是直接追求完整视频

在正式视频生成前，可以先生成“低成本动态分镜”：真实/接近最终的语音 + 简化或低清画面 + 基础镜头运动 + 粗略音效/音乐层。其目的不是展示最终画质，而是验证故事是否成立。

这样用户可以在非常低的成本下发现：“这里其实应该用反应镜头”“这句话说完应该留 0.5 秒”“下一镜头不需要正面，而应该从侧后方接过去”。只有结构与节奏通过，再进入正式画面生成。

### 14.10 音频可编辑性的“入口设计”建议继续沿用前三层模型

| 入口 | 示例 | 最终转换 |
|---|---|---|
| 用户表达意图 | “她这句说得太平了，要压低一点，像是在威胁。” | Audio Intent → 局部重新生成 |
| 输入想法 | 用户拖动一段对白块、拉长停顿、改变角色顺序 | Timing / Structure Intent → 重新组织 Audio Event |
| 视觉指向 | 点击人物嘴部/脸部，指出“这里的情绪要更克制” | Audio + Visual Intent 联动 |
| 执行指令查看 | 系统显示“理解为：语速 -15%、停顿 +0.4s、情绪强度 +1” | 用户可接受、修改或直接取消 |

这样既保留用户的自由表达，又避免“AI 自动执行后用户不知道改了什么”。

### 14.11 与 Scene / Transition / Continuity 的最终连接

| 对象 | Audio 在其中扮演什么角色 | 与视频的关系 |
|---|---|---|
| Scene | 保存当前段落的语音事件、角色、节奏与声音意图 | 决定镜头时长与可选镜头组织 |
| Transition | 提供对白结束、停顿、情绪变化等时间线索 | 触发声音先行、反应镜头、切视线等过渡策略 |
| Continuity State | 保存角色声线、说话风格、关系状态、已知信息 | 与人物视觉身份和情绪状态保持一致 |
| Branch | 不同配音/语气/对白节奏可以对应不同叙事路线 | 同一个故事节点可以有不同“听法”和“看法” |
| Preview | 让用户先听节奏，再审画面 | 480P 视觉 + 可判断音频构成导演审片 |

### 14.12 质量工艺：最终产物的“好看”不等于模型单镜头质量高

一旦产品开始主动承担叙事组织，最终品质的检查标准也应该从“每个镜头漂亮不漂亮”扩展到“镜头、声音、表演、剪辑共同是否成立”。建议至少关注以下工艺层：

- **表演连续：** 角色在相邻镜头的情绪、说话方式、动作状态要有上下文，而不是每镜头重新随机表演。
- **对白与剪辑：** 不要机械地“句尾必切”。有时应该切在说到一半、留住听者反应，或让声音跨过画面切换。
- **声音空间一致：** 环境声、底噪、距离感、空间混响不要随着 Scene 切换突然断裂；否则画面连续，耳朵却会感到“跳”。
- **信息层级：** 声音已经解释清楚的内容，画面未必需要再次说明；可把视觉资源让给人物关系、空间或情绪。
- **留白：** 不是所有时间都要填满对白、动作和音乐。沉默本身也应成为可设计的叙事元素。
- **局部重做：** 正式制作后，最好能只替换一句对白、一个镜头或一段 Transition，而不是因为小修改导致整条成片重新生成。

因此最终产物需要一种“模块化可重渲染”的工艺思维：用户修改局部时，系统尽量只让受影响的局部重做，并维持未修改部分的身份、节奏和连续性。

### 14.13 几个可作为后续产品差异化的创意表达

- **“先听，再拍”**：先生成多角色语音与基本表演节奏，系统自动铺出一版动态分镜，再决定每段如何拍。
- **“声音就是一根线”**：对白、呼吸、停顿、环境声可以像一条不可见的叙事线，跨越多个 Scene 把故事串起来。
- **“一句话生成镜头建议”**：用户输入/生成一句关键台词，LLM 自动给出 2–3 种反应镜头与转场方式，而不是只给一个 Video Prompt。
- **“听法分叉”**：不仅能分叉镜头，也能分叉同一句对白的语气、速度、停顿，从而产生不同的情绪版本，再比较哪一种更适合后续画面。
- **“锁一层，重做另一层”**：用户可以锁住 Audio、只重做 Visual；也可以锁住 Visual、重做 Audio。这个能力可以成为 AI 创作里很重要的可控性。
- **“声音先到，画面后到”**：把声音先行/画面后延作为一等公民，而不是传统剪辑里的高级术语，让 AI 自动寻找更有叙事感的切法。

### 14.14 本轮形成的阶段性判断

1. Audio Gen 不应被降级为“配音工具”，它有潜力成为叙事输入、时间锚点和人物连续性的一部分。
2. Audio 与 Video Prompt 不建议争夺永久的“主导权”。更合理的是：上层由 Narrative Intent 主导；Dialogue-led 场景以 Audio 为时间骨架；Visual-led 场景以 Visual 为骨架；混合场景由两者共同构成节拍。
3. Audio 的核心可编辑对象不应该只是整条音轨，而应该是可局部修改、可重排、可重新生成的 Audio Event / 表演事件。
4. 剪辑的地位会变化，但不会消失：系统把大量“技术性拼接”前移为 Scene / Transition / Audio / Continuity 的生成约束，把后期剪辑重新留给节奏、视线、信息揭示和审美选择。
5. 480P Preview 更应该是“动态分镜 / 导演审片”，而不是低画质成片预览；在这里声音的判断价值甚至可能高于画面细节。
6. 最终品质要关注“视听整体成立”，尤其是声音连续性、对白节奏、留白、镜头切点、局部可重做与整体可控性。

## 附录 A｜本轮思维碰撞中的关键原始判断

以下保留本轮讨论中容易被“总结稿”压掉、但对后续继续设计有价值的具体判断：

- “拖拽应该成为第一语言”：重点不是让画布有拖拽，而是让拖拽动作本身表达“创建、归属、排序、连接”等意图。
- “吸附应该是语义吸附”：吸附到左边、右边、内部、两个镜头之间，应该对应不同含义；否则吸附只是视觉效果。
- “不要把 X 轴直接当时间”：二维空间更适合讲故事，时间轴保留给精确时间。
- “Scene 卡片应该像小编辑器”：用户尽可能在当前空间完成镜头修改，而不是来回跳页面。
- “连线不是默认存在”：全部关系都画出来，会把产品推成复杂节点图；因此连线应有语义才出现。
- “真正值得创新的是 Scene 之间的叙事衔接”：两个单镜头都很好，并不意味着拼接自然，产品应直接帮助用户解决“怎么从 A 讲到 B”。
- “LLM 可以像导演一样提供多种衔接策略”：连续运动、特写/视线、时间跳跃、视角切换等，但最终选择权在创作者。
- “场景一致性不只是参考图相似”：应该维护跨 Scene 的 Continuity State，包括人物、服装、道具、动作状态、空间、镜头方向、情绪等。
- “Preview 不只是预览”：480P 是低成本试错与审片环节，正式生成应尽量后置。
- “修改不是调参数，而是表达问题”：用户可以说“太快”“这里不自然”“保持右手拿伞”，系统负责把它变成执行计划。
- “指哪改哪”值得重点挖掘：点击人物、背景、画面区域后，修改入口可以自动带上下文。
- “画箭头表达镜头运动”是典型创新入口：用户直接画视觉意图，系统再转成可执行镜头运动。
- “分叉是叙事探索”：不是简单复制文件，而是保留不同 Transition 方案并比较。
- “一主一辅交付给施工方”：研究记录保留上下文；施工方案负责明确执行边界。
- “产品语义明确、工程实现留空间”：更了解项目代码的施工方应该有技术决策权。
- “Audio Gen 不应只是音轨”：在多角色短片中，语音可以承担人物关系、表演、节奏与时间锚点。
- “不是 Audio vs. Video”：上层应由 Narrative Intent 统一；不同 Scene 可以动态采用 Dialogue-led、Visual-led 或 Co-led 的时间骨架。
- “Audio Event 而不是整条音轨”：对白、角色、语气、速度、停顿、时间与 Voice Identity 都应成为可局部编辑的对象。
- “先听，再拍”：真实/接近最终的声音先成立，可以反推 Scene 时长、反应镜头、声音先行/后延和 Transition。
- “剪辑不消失，而是升级”：生成阶段解决大量技术性拼接，人工剪辑保留在节奏、信息揭示、视线和审美判断上。
- “模块化重渲染”：小修改尽量只重新生成受影响的 Audio Event / Scene / Transition，不让局部修改破坏整条成片。

## 附录 B｜当前建议的最小闭环

**拖拽构建 → Scene 表达 → Audio / Visual Intent 汇合 → Scene A/B 关系 → Continuity Check → LLM 提出 Transition Intent → Audio / Video 动态分镜 Preview → 用户自然语言/点击/画轨迹/编辑对白修改 → 再 Preview → 局部分叉比较 → 正式生成。**
